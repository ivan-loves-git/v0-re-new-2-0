# Phase 1.1 Context: Testing Environment and Release Protocol

## Why This Phase Exists

Phase 1 added real database-backed opportunity features. Continuing to Phase 2 without a testing and release protocol would increase product and data risk.

This phase creates the operating discipline for Re-New development:
- where migrations are applied,
- how test data is created,
- how UAT is recorded,
- when branches are pushed or merged,
- how rollback is handled.

## Product Principle

Re-New data is more valuable than velocity. Code can be reverted in GitHub; database changes need explicit backup, environment, and rollback decisions.

## Recommended Default

Use a separate Supabase test project for Phase 1 validation.

Ivan confirmed this direction on 2026-05-17. The current/shared Supabase database is not an approved test target for Phase 1.1.

## Locked Decision

Phase 1.1 uses Option 1: a separate Supabase test project.

This means:
- Phase 1 migrations are applied only to the test Supabase project.
- Fake or sanitized test data is used for UAT.
- The worktree `.env.local` must point to the test project.
- No production/current Supabase migration happens during this phase.
- Phase 2 remains blocked until the test environment and UAT gate pass.

## In-Scope

- Environment decision and documentation.
- Worktree test setup.
- Supabase migration safety protocol.
- Phase 1 UAT checklist and result log.
- GitHub/GSD/Linear release responsibilities.
- Creating or configuring the separate test Supabase project.
- Applying Phase 1 migrations to the test Supabase project.

## Out-of-Scope

- Building Phase 2 features.
- Production deployment.
- Full CI/CD automation.
- Applying migrations to the current/shared Supabase database.
- Large database cloning unless explicitly needed.
